# BuildShield Core v1.0.0

Primera versión estable del **backend**, con IAM, Organización, Inventario, Pedidos y Auditoría dentro de un monolito modular. PostgreSQL conserva el estado operativo y la bitácora complementaria; no se implementa Event Sourcing (reconstrucción del estado reproduciendo eventos).

## Alcance y contrato

El flujo implementado permite registrar una empresa, iniciar sesión, configurar usuarios/asignaciones/obras/almacenes/materiales, registrar existencias, crear y aprobar/rechazar pedidos, y consultar resultados e historial.

- IAM: JWT RS256, usuarios por organización, renovación y cierre de sesión, recuperación de contraseña.
- Organización: administración y visibilidad de obras, almacenes, materiales y asignaciones.
- Inventario: consultas, entradas y fachada de descuento; saldo, movimiento y auditoría se confirman juntos.
- Pedidos: creación y decisiones consistentes. Aprobar mantiene Registrado → EnRevision; no reserva ni descuenta stock.
- Auditoría: registro de cambios y denegaciones; GET /api/v1/audit/events exclusivo del administrador, filtros por recurso y páginas de 50 registros por defecto, máximo 100.

OpenAPI local: /api/v1/api-docs y /swagger-ui.html. La [colección Postman](../postman/BuildShield-Sprint1.postman_collection.json) conserva claves de operación para sus reintentos.

### Idempotencia obligatoria

Estos POST requieren Idempotency-Key con un UUID:

- /api/v1/stock/entries
- /api/v1/orders
- /api/v1/orders/{id}/approve
- /api/v1/orders/{id}/reject

Una intención nueva utiliza una clave nueva. Para reintentar después de perder la conexión, conservar clave, datos, ruta y parámetros. Dentro de 24 horas se recuperan estado HTTP, cuerpo y Location originales. Se rechazan cambios de identidad, contenido o permisos. Una operación en curso responde 409 con Retry-After; una respuesta vencida o una clave legacy no vuelven a ejecutar el negocio.

Todos los errores y tiempos de espera se describen en [backend-hardening.md](../backend-hardening.md). Esta versión fija esas obligaciones para futuros clientes; todavía no existe frontend.

## Instalación y migraciones

Requisitos: Java 21 y PostgreSQL. Consultar la documentación principal para conexión y claves RSA. El JAR ejecutable requiere la misma configuración que la aplicación; no incorpora contraseñas, claves privadas ni una base de datos.

Flyway aplica, además de las migraciones publicadas:

| Migración | Cambio |
|---|---|
| V13 | Conserva actor, rol, huella y Location de idempotencia; marca respuestas retiradas sin borrar la operación |
| V14 | Crea auditoría y protecciones de solo anexado sobre bitácora y movimientos |
| V15 | Añade relaciones compuestas por empresa dentro de Inventario y Pedidos |

Las migraciones antiguas permanecen intactas. El upgrade conserva datos válidos; una relación histórica incompatible se rechaza sin corregirla silenciosamente.

Separar las cuentas:

- Ejecución local: CORE_DB_USER / CORE_DB_PASSWORD.
- Migración local: CORE_DB_MIGRATION_USER / CORE_DB_MIGRATION_PASSWORD; si se omiten, se conserva la compatibilidad local anterior.
- Ejecución prod: DB_USER / DB_PASSWORD y DB_URL.
- Migración prod: DB_MIGRATION_USER / DB_MIGRATION_PASSWORD, distintos de los de ejecución.

Aplicar los permisos de [runtime-role.sql](../database/runtime-role.sql) como propietario/migrador. La cuenta de ejecución no debe ser superusuario ni dueña de tablas. Las pruebas usan bases temporales independientes y una cuenta de limpieza distinta de la productiva.

El perfil prod también requiere un adaptador real de correo: el adaptador de log disponible es exclusivo de local/test. El alcance estable del backend no declara un despliegue productivo completado.

## Evidencia y archivos de entrega

El commit de implementación [3b336a2](https://github.com/upc-pre-202620-1asi0657-9222-BobBuilder/buildshield-core/commit/3b336a2b3d5d6446f25b68730ad0e8b11cf69d62) tuvo 479 pruebas unitarias y 181 de integración/aceptación sin fallos ni omisiones, y 99,80 % de cobertura de líneas en dominio/aplicación.

La carga del 5 de octubre de 2026 utilizó 50 clientes simultáneos durante 60 segundos: 99 677 consultas, 0 errores y p95 entre 74,81 y 77,56 ms. Aplicación, PostgreSQL y generador compartían una máquina; dataset pequeño y una sesión de administrador compartida. Es una medición anterior, no una carga nueva de esta release.

Resultados y matriz: [verification/README.md](../verification/README.md). La preparación de esta versión vuelve a ejecutar mvn verify y comprueba la imagen Docker mediante GitHub Actions. La GitHub Release enlaza los resultados de su commit final.

Se entregan buildshield-core-1.0.0.jar y buildshield-core-1.0.0.jar.sha256 procedentes de la ejecución exitosa de main. SHA-256 es la huella que permite comprobar que el archivo descargado coincide con el publicado. La imagen Docker se construye como verificación; este proceso no publica imágenes en un registro ni despliega el sistema.

## Pendientes y límites

- Despachos, Recepciones, sus flujos completos y reservas automáticas.
- Pagos/suscripciones y cambios de proveedor.
- Cadena de huellas y exportación de custodia.
- Disponibilidad mensual, conmutación de infraestructura, escalado horizontal y 500 recepciones concurrentes.
- Frontend y funcionamiento offline.

QAS02 se verifica en descuentos de Inventario, pero falta el flujo de Despachos. QAS04 tiene evidencia en los módulos actuales. QAS05/QAS09 tienen historial protegido, pero falta custodia/exportación. QAS01, QAS03, QAS06, QAS07, QAS08 y QAS10 siguen pendientes en su alcance completo. Los resultados actuales no acreditan esos escenarios futuros.

## Desarrollo posterior

main conserva versiones entregadas. develop integra el siguiente trabajo y queda en 1.1.0-SNAPSHOT. Las ramas feature/* y fix/* nacen de develop y se eliminan después de integrarse. release/* prepara versiones; hotfix/* atiende correcciones urgentes desde main y vuelve a ambas ramas permanentes.

Los commits representan cambios coherentes y comprobables. Los PRs conservan esos commits mediante merge commit; el tag anotado v1.0.0 identifica exactamente la entrega. Nunca se mueve un tag publicado para representar otros cambios.
